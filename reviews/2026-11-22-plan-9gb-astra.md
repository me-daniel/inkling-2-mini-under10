# Draft concept: an own-encoded ~9 GB GGUF of Inkling 2 Mini for a 16 GB Mac

## Model
- thinkingmachines/Inkling-2-Mini, 26.07 B params, looped MoE: 24 layers, layers 6-17 are the looped core, default P = 3 passes, so 48 layer visits. 128 routed experts per layer in two tensors: ffn_gate_up_exps (2304 inputs) and ffn_down_exps.
- Quality metric: mean KL to a Q8_0 reference at P = 3 (llama-perplexity --kl-divergence). S = selection set (WikiText-2 test text), T1 = held-out prose, T2 = held-out reasoning traces (GSM8K, model-generated). Differences are paired over chunks with bootstrap 95% CI.

## Landscape near 9 GB (HF file sizes)
- Unsloth: UD-IQ1_S 7.76 GB, UD-IQ1_M 8.02, UD-IQ2_XXS 8.49, UD-Q2_K_XL 9.14 (9,138,715,328 B), UD-IQ3_XXS 11.66.
- AtomicChat: AD-IQ2_XXS-Q2 7.90, AD-IQ2_M 8.67, AD-IQ2_XXS 10.43.
- bartowski: smallest is IQ2_XXS 10.32 GB. Many other repos not yet checked (APEX variants, GSQ-RCO, NInfer repacks of UD).
- UD-Q2_K_XL tensor types (from its header): gate_up IQ1_S in layers 0-4 and 6, IQ2_XXS in 5, 7, 12-14, IQ2_XS in 8 and 10, IQ2_S in 9, 11, 15-23. down: Q2_0 in 0-4, 6, 12-14, 21-23; NVFP4 in 5, 7-11, 15-19; MXFP4 in 20. Attention mostly Q8_0 / Q6_K, output Q4_K, embeddings IQ4_XS. Its imatrix: "imx_s0.conv.jsonl", 8238 chunks (conversation data).
- Stock llama.cpp's Metal backend cannot multiply NVFP4, so those tensors run on the CPU. The sibling measured UD-IQ3_XXS (20 NVFP4 expert tensors) at 68 t/s prompt and 10.9 t/s generation versus about 225 / 19 t/s for all-Metal files of similar size on an M5 Pro. Unsloth's own llama.cpp fork already runs NVFP4 on Metal.

## Measured so far (this repo and the sibling repo, same metric)
1. At UD-IQ2_XXS's exact per-tensor types, plain llama-quantize with an imatrix (M0) is +0.02727 KL behind UD on S. UD's edge by tensor class: gate_up 61%, non-expert 23%, down 15%. The edge is the encoder, not the type map or the imatrix (three imatrices differ by < 0.0004).
2. Attenuation: fits that lower per-layer MSE shrink each row's output gain <q,w>/<w,w> below 1, and over 48 visits this costs KL. A mean-aware gate_up scale refit lowered full-Gram error in 128/128 experts and still raised KL by +0.072 (gain 0.79). The same refit with each row restored to llama-quantize's own gain gained -0.0038. Rescaling our Q2_0 down from gain 0.86 to 1 gained -0.0070. Gain 1 is not universal: it hurt gate_up and UD's own Q2_0 down (gain 0.90).
3. Our best own file at 8.49 GB (M0rk: mean-aware gate_up refit + gain restore, gain-1 Q2_0 down, all tensors in Metal types) closes 40% of the gap to UD on S. Held out: M0rk minus UD-IQ2_XXS +0.01424 on T1, +0.01662 on T2; it beats both AtomicChat files on both sets (-0.016 to -0.041).
4. The sibling's full-Gram code refinement (changes grid indices and signs, keeps scales, objective tr(E H E^T) with H = Gram + 0.1 diag shrink, gain floor per row) for IQ2_S / IQ3_XXS gate_up at 11.6 GB: closes 93% of the gap to UD-IQ3_XXS on S, 74% on T1, 18% on T2. Its Grams are WikiText-2 train only (same source as S), about 5k tokens per median expert for 2304 dims. The refiner does not support IQ1_S, IQ2_XXS or IQ2_XS.
5. Sibling's block map (one block of experts quantized, rest at reference, S): looped blocks and the last block are the most sensitive at 2 bits; per-layer KL B1 (0-5) 0.0046, B2 (6-11) 0.0104, B3 (12-17) 0.0142, B4 (18-19) 0.0180, B5 (20-23) 0.0167.
6. The sibling's 11.5 GB file (v1) is public: it failed its gate against UD-IQ3_XXS and was released as the closest-to-original all-Metal file under 12 GB, 1.75x faster generation than UD-IQ3_XXS on stock llama.cpp.

## Proposed plan for the 9 GB tier
- Target: one own-encoded GGUF, every tensor in a type stock llama.cpp runs on Metal, size <= 9,138,715,328 B (UD-Q2_K_XL), so it fits a 16 GB Mac's default GPU memory with room for context.
- Step 0: landscape. List every GGUF of this model in 8.0-9.2 GB on HF with its types and off-Metal tensor count. Score UD-Q2_K_XL and any all-Metal comparator on S, T1, T2. Measure stock-llama.cpp speed of ours vs UD-Q2_K_XL.
- Step 1 (baseline M1): llama-quantize at UD-Q2_K_XL's per-tensor types, with each NVFP4 down replaced by IQ4_NL (same 4.5 bpw, on Metal). Check size and that MXFP4 runs on Metal.
- Step 2 (M1rk): apply the M0rk recipe (mean-aware gate_up refit with per-row gain restore; Q2_0 down rescaled to gain 1).
- Step 3 (M1rr): the sibling's full-Gram code refiner on the 11 IQ2_S gate_up layers, with Grams captured on mixed calibration (prose, chat, reasoning traces) and more tokens, then the gain restore.
- Step 4: spend any bytes left under the limit by the block map (looped and last blocks first).
- Gate: lower KL than every all-Metal file <= the limit on T1 and T2 (CI below 0), and report the difference to UD-Q2_K_XL whatever it is. A held-out T3 for the final file.
- Release bar (open, for the owner): only own encodings. Is "best all-Metal own encoding at this size + faster than UD on stock llama.cpp" enough, as for the sibling's v1, or must it beat UD-Q2_K_XL?

## Constraints
- One Apple M5 Pro Mac, 48 GB, ~30 GB per heavy run, shared with a sibling project that is using the GPU now. No cloud GPU. A full S score takes minutes; a Gram capture for a few layers takes about an hour; the sibling's refiner took hours for 24 layers.
- Stock llama.cpp types only (the file must run in stock llama.cpp, LM Studio, Ollama).

## Reply (verbatim)

## Design review

1. **The byte cap comes from a competitor’s file. The 16 GB use case still needs a budget.** At 9,138,715,328 bytes, the weights occupy 8.51 GiB. The draft specifies no context length, KV-cache types, batch size, or allowance for vision. Pick a workload before choosing the cap. For example, require one text session to prefill 7,168 tokens and generate 1,024 more at P = 3 with default macOS memory settings. Measure peak footprint, memory pressure, swap growth, time to first token, and sustained decode. A 48 GB M5 Pro can screen candidates and estimate allocations. Only a run on a named 16 GB configuration verifies the fit and speed claim.

2. **The comparator search excludes files covered by the gate.** Step 0 starts at 8.0 GB, while the gate says *every* all-Metal file under the cap. AtomicChat alone lists 6.88, 7.26, and 7.90 GB candidates. Conversely, a 10.32 GB file that fits the chosen workload matters to the Mac buyer even though it falls outside the byte-cap experiment. Inventory both groups, verify base-checkpoint identity, sum shards, and deduplicate repacks by tensor payload. Record the search date and revisions. Unsloth explicitly directs stock llama.cpp users to `Mainline_Support`, so hash that artifact and check its layout before treating the quoted header, byte count, or timing as the stock baseline. [AtomicChat file table](https://huggingface.co/AtomicChat/Inkling-2-Mini-GGUF) · [Unsloth runtime instructions](https://huggingface.co/unsloth/Inkling-2-Mini-GGUF) · [Mainline files](https://huggingface.co/unsloth/Inkling-2-Mini-GGUF/tree/main/Mainline_Support)

3. **The cleanest missing control is a substitution-only GGUF.** For diagnosis, keep the mainline UD-Q2_K_XL tensors fixed except for the 11 NVFP4 downs. Encode those downs from the same source checkpoint into IQ4_NL. Compare that file with UD to measure the substitution’s KL and speed cost, then with M1 to measure the aggregate difference from re-encoding the remaining tensors. This control costs 11 tensor encodes and is never a release candidate. It matters because the published checkpoint already uses NVFP4 and MXFP8. Check whether UD preserved the native expert values and scales. Equal bits per weight can still mean paying a second quantization error. [Original checkpoint numerics](https://huggingface.co/thinkingmachines/Inkling-2-Mini)

4. **The claimed encoder attribution is too strong.** Three imatrices changing your result by less than 0.0004 establishes insensitivity across those three runs. It does not isolate Unsloth’s source conversion, scale handling, calibration coverage, or encoder. Likewise, the 61%/23%/15% split needs the tensor-swap order and the residual interaction. In a routed model, improving one tensor class can change which experts receive the next layer’s inputs. Treat those percentages as measurements at the 8.49 GB map until a swap at the 9.14 GB map reproduces them.

5. **Gain restoration has an empirical effect. The proposed loop mechanism remains open.** The reported row gain is a projection in weight space. Routed activations, nonlinear gates, and residual connections make it unsafe to compound that scalar across 48 visits. At M1, score gate-up restoration alone, down rescaling alone, and both. On a small fixed batch, log the expert-output norm, residual-stream error, and route agreement against Q8 after each core pass. If KL improves without progressively reducing pass-to-pass drift, retain the recipe and drop the causal explanation.

6. **Step 3 bundles changes and extrapolates from the weakest transfer result.** The sibling recovered 93% of its gap on S and 18% on reasoning traces, at a different size and with different supported types. Here the refiner reaches only 11 of 24 gate-up tensors. Pilot one IQ2_S layer on the actual M1rk background. Compare refined and unrefined codes under the same gain policy. Compare old and mixed calibration at equal token counts before paying for more tokens. Record routed examples per expert and pass, particularly the lower tail. A median of 5,000 examples for 2,304 dimensions says little about the least-observed experts. Use absolute KL deltas on separate prose and reasoning development samples to decide whether to scale up.

7. **The block map does not justify “looped and last first.”** B4, layers 18–19, has the largest reported per-layer damage at 0.0180 and lies outside the loop. More importantly, damage from degrading one block against reference weights answers a different question from the benefit of upgrading that block inside M1rk. Try equal-byte promotions in B3, B4, and B5 on the candidate itself, rank by end-to-end KL improvement per added byte, and verify the winning combination together. Also calculate the exact serialized size before planning Step 4. Replacing 4.5 bpw with 4.5 bpw creates no expected tensor-payload savings.

8. **T1 and T2 have already informed the design.** Keep them as regression sets and give T3 a decision rule now. Freeze the finalist, comparators, prompts, tokenization, Q8 reference logits, and scoring windows before opening fresh prose documents and fresh reasoning problems. Bootstrap paired differences by document or problem, keeping all chunks and traces from one source together. Record the T2 generator and decoding settings. Its teacher-forced trace KL measures fidelity on that generator’s trajectories. For a claim about reasoning, also score final-answer accuracy from fresh prompts under identical generation budgets. For a claim about fidelity to the *original*, spot-check the finalist ranking against the native or faithfully dequantized checkpoint. Unsloth’s published KL uses UD-Q8_K_XL as its reference and cannot fill in your missing Q8_0 measurements. [Unsloth evaluation table](https://huggingface.co/unsloth/Inkling-2-Mini-GGUF)

9. **The speed claim needs the exact pair of files and execution traces.** The sibling timed a different file with 20 NVFP4 expert tensors. Your map has 11, distributed across layers with different visit counts. Pin the stock commit and inspect backend placement for the routed matrix multiplications during both prefill and decode, including the MXFP4 layer. A header or a log saying all layers were offloaded cannot establish this. Benchmark UD-Q2_K_XL, the substitution-only control, M0rk, and the finalist in alternating order on an idle GPU with identical prompts, context occupancy, KV types, batch settings, and no speculative decoding. Run the same UD file on the fork as a separate check on how much of the advantage depends on the runtime. Verify load *and generation* on named LM Studio and Ollama versions before claiming compatibility. [Stock Metal operation checks](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m)

10. **Set the falsifier before building.** Define Δ as candidate KL minus comparator KL. One eligible all-Metal comparator with a paired interval wholly **above zero** for Δ on either required domain is evidence against the “best on both” claim. An interval crossing zero leaves the claim unresolved and fails the proposed release gate. Separately, a routed expert multiplication falling back to CPU falsifies the all-Metal claim for that build and workload. Failure to sustain the declared context on the target Mac falsifies the fit claim. The brief supplies no run manifests, per-document scores, dispatch traces, or 16 GB measurements from which I could independently verify those outcomes.

11. **A cheaper design answers the same release question.** Start from the own-encoded M0rk and use the roughly 0.65 GB difference to the proposed cap for two competing, equal-byte promotions from source weights. Spend one on gate-up tensors and one on downs, using the block test in point 7 to choose locations. Score both against untouched M0rk and the strongest eligible public baseline using cached reference logits. Advance at most one to fresh evaluation. This tests whether an own-encoded file can win at the cap without a new Gram capture, an encoder port, or a full M1-to-M1rr ladder.

## Which path to run

12. **I would spend the next few days on a context-qualified 16 GB GGUF, starting from M0rk.** Let the workload determine the file size. The 8.49 GB artifact already exists, has measured held-out gaps, and gives you a direct way to price each additional allocation of bits. “Own-encoded, about 9 GB, for Apple silicon” is already crowded territory. One publisher lists a separate 8.87 GB Inkling pack for an Apple-silicon MLX runtime. It belongs in the landscape for the broad Mac claim, outside the stock-GGUF ranking. The distinction worth pursuing is a measurable one: the highest fidelity among audited stock GGUFs that sustain a specified context and interactive speed on a specified 16 GB Mac. [8.87 GB Apple-silicon model card](https://huggingface.co/shinmegamiboson/Inkling-2-Mini-LookAtMyQuant-8.9GB)

13. **First step — freeze the workload and audit while the GPU is occupied.** I would use the 8,192-token text session in point 1 as the initial product assumption. Set the acceptable prefill time, decode floor, and maximum acceptable KL deficit to UD *before* seeing candidate scores. Build the dated inventory from headers and manifests. Include the closest larger stock GGUF that might fit and identify whether a real 16 GB validation run is available.

14. **Second step — measure what a user can download today.** In the first idle GPU window, run M0rk, mainline UD-Q2_K_XL, and the strongest plausible all-Metal competitors at the chosen workload. Record quality, occupancy-dependent speed, placement, and memory together. Use these measurements to identify the actual deficit. If M0rk already meets the release bar, take it directly to fresh and target-device validation.

15. **Third step — build one challenger for the measured deficit.** If M0rk has runtime headroom and loses on quality, run the equal-byte promotion pilot in point 11 within the measured headroom. Freeze the winner and run the fresh evaluation once. If memory is the binding constraint, test one smaller own-encoded variant at the same context instead. Either branch produces one candidate with a stated reason for its size.

16. **Stop rule and release decision.** Stop encoding if an existing stock GGUF meets the workload, matches or beats the candidate’s quality on both domains, and matches or beats its speed within the prespecified practical margins. Also stop the multi-day refinement if neither cheap promotion clears the development threshold. **Beating UD-Q2_K_XL on KL is optional for a speed-qualified release.** Release requires a material stock-runtime advantage, a preaccepted quality deficit to UD, and a demonstrated advantage over the best *other fast file* at the target workload. Own provenance plus beating a CPU-fallback baseline on the 48 GB machine does not clear that bar. Without a 16 GB run, the defensible deliverable is a stock-GGUF benchmark with an estimated memory budget.
